# MQTT Telemetry Simulator

A Python-based MQTT Telemetry Simulator that generates realistic simulated EV battery telemetry data and provides different normal and anomaly scenarios for testing telemetry monitoring, validation, and security concepts.

The project simulates battery telemetry events similar to data that could be generated by a Battery Management System (BMS). It supports normal telemetry as well as delayed telemetry, duplicate packets, out-of-range values, missing timestamps, spoofed battery identity, and replay attacks.

The project provides:
- Python-based telemetry generation
- Scenario-based anomaly simulation
- FastAPI REST API
- Streamlit dashboard
- Pydantic data validation
- Automated testing with pytest
- Code coverage with pytest-cov
- MQTT-style topic and QoS metadata
- CSV and JSON data handling
- Security-focused telemetry scenarios
- QA, verification, security and release documentation

---

## Project Overview

The MQTT Telemetry Simulator was developed to provide a software-based environment for generating and testing simulated EV battery telemetry without requiring real BMS hardware or a real MQTT broker.

The simulator generates parameters such as:

- Battery ID
- Voltage
- Current
- Temperature
- State of Charge (SOC)
- State of Health (SOH)
- Timestamp
- Event ID
- Sequence Number
- MQTT-style topic
- QoS
- Simulation status
- Anomaly information

The project is useful for testing telemetry trust, anomaly detection concepts, replay attack detection and monitoring workflows.

---

## Problem Statement

Real EV battery telemetry normally comes from physical Battery Management Systems and connected hardware.

Testing telemetry security and anomaly scenarios directly on real hardware can be difficult because it may require:

- Battery hardware
- Sensors
- BMS
- MQTT infrastructure
- Network communication
- Additional testing equipment

This project provides a local software simulator that can generate telemetry events and intentionally introduce different abnormal conditions for testing.

# Telemetry Data Model

The main telemetry model is implemented using Pydantic.

The battery telemetry contains:

```text
battery_id
voltage
current
temperature
soc
soh
timestamp
```

Additional event-level information is added by the scenario engine:

```text
event_id
sequence_number
topic
qos
simulated
anomaly
```

Some scenarios also add:

```text
sent_at
```

for representing delayed or replay-related timing information.

---

# MQTT-Style Telemetry Metadata

The simulator does not create real MQTT network traffic.

Instead, generated events contain MQTT-style metadata for simulation and testing.

Example topic:

```text
battery/telemetry/BAT001
```

Example metadata:

```json
{
  "topic": "battery/telemetry/BAT001",
  "qos": 1,
  "simulated": true
}
```

The `simulated` field clearly indicates that the event is generated by the simulator.

---

# Telemetry Scenarios

The project supports seven scenarios.

| Scenario | Purpose | Anomaly |
|---|---|---|
| Normal | Generate valid battery telemetry | None |
| Delayed | Simulate delayed telemetry | `DELAYED` |
| Duplicate | Simulate repeated sequence number | `DUPLICATE` |
| Out of Range | Simulate abnormal sensor values | `OUT_OF_RANGE` |
| Missing Timestamp | Remove timestamp from event | `MISSING_TIMESTAMP` |
| Spoofed ID | Simulate unauthorized battery identity | `SPOOFED_ID` |
| Replay Attack | Simulate previously generated telemetry | `REPLAY_DETECTED` |

---

## 1. Normal Telemetry

The normal scenario generates valid simulated battery telemetry.

Example:

```json
{
  "battery_id": "BAT001",
  "voltage": 48.2,
  "current": 12.5,
  "temperature": 32.4,
  "soc": 78.5,
  "soh": 96.2,
  "timestamp": "2026-01-01T10:00:00"
}
```

No anomaly is generated for the normal scenario.

---

## 2. Delayed Telemetry

The delayed scenario simulates telemetry that arrives later than the original timestamp.

The simulator creates a `sent_at` value after the configured delay.

Example:

```json
{
  "battery_id": "BAT001",
  "timestamp": "2026-01-01T10:00:00",
  "sent_at": "2026-01-01T10:00:10",
  "anomaly": "DELAYED"
}
```

The delay can be configured using the API or Streamlit dashboard.

---

## 3. Duplicate Packet

The duplicate scenario simulates repeated telemetry using the same sequence number.

Example:

```json
{
  "sequence_number": 1,
  "anomaly": "DUPLICATE"
}
```

This scenario is useful for testing duplicate event detection.

---

## 4. Out-of-Range Values

The out-of-range scenario generates telemetry values outside the defined normal limits.

Example simulated values include:

```text
Voltage       = 65.0 V
Temperature   = 75.0 °C
Current       = 600.0 A
```

The generated event contains:

```json
{
  "anomaly": "OUT_OF_RANGE"
}
```

---

## 5. Missing Timestamp

The missing timestamp scenario removes the timestamp field from the telemetry event.

Example:

```json
{
  "battery_id": "BAT001",
  "voltage": 48.2,
  "current": 12.5,
  "anomaly": "MISSING_TIMESTAMP"
}
```

This scenario helps test validation of incomplete telemetry.

---

## 6. Spoofed Battery ID

The spoofed identity scenario generates a simulated battery identity different from the original battery ID.

Example:

```text
SIM-SPOOF-001
```

The event is marked as:

```json
{
  "anomaly": "SPOOFED_ID"
}
```

The `SIM-SPOOF-` prefix makes the simulated identity easy to identify.

---

## 7. Replay Attack

The replay attack scenario simulates previously generated telemetry being reused.

The event timestamp is moved into the past while a new `sent_at` timestamp is generated.

Example:

```json
{
  "timestamp": "2026-01-01T09:55:00",
  "sent_at": "2026-01-01T10:00:00",
  "anomaly": "REPLAY_DETECTED",
  "simulated": true
}
```

This scenario is used to demonstrate a replay attack detection concept.

# FastAPI

The project provides a FastAPI REST interface.

Start the API using:

```bash
python -m uvicorn api:app --reload
```

The API runs locally at:

```text
http://127.0.0.1:8000
```

Swagger documentation is available at:

```text
http://127.0.0.1:8000/docs
```

---

## API Endpoints

### GET `/`

Checks whether the API is running.

Example response:

```json
{
  "message": "MQTT Telemetry Simulator API is running"
}
```

---

### GET `/health`

Health check endpoint.

Example:

```json
{
  "status": "healthy"
}
```

---

### GET `/scenarios`

Returns the available telemetry scenarios.

Example:

```json
{
  "scenarios": [
    "normal",
    "delayed",
    "duplicate",
    "out_of_range",
    "missing_timestamp",
    "spoofed_id",
    "replay_attack"
  ]
}
```

---

### POST `/generate-events`

Generates telemetry events based on the selected scenario.

Example request:

```json
{
  "battery_id": "BAT001",
  "scenario": "normal",
  "count": 3,
  "delay_seconds": 10
}
```

Example replay attack request:

```json
{
  "battery_id": "BAT001",
  "scenario": "replay_attack",
  "count": 2,
  "delay_seconds": 10
}
```

The API response contains the generated events and scenario information.

---

### GET `/sample`

Returns one sample telemetry event.

Example:

```json
{
  "sample": {
    "battery_id": "BAT001"
  }
}
```

# Project Limitations

The current simulator has some limitations:

- It does not connect to a real MQTT broker.
- It does not communicate with real BMS hardware.
- It does not collect telemetry from physical sensors.
- MQTT communication is represented through simulated topic and QoS metadata.
- Streamlit is a local dashboard.
- Security scenarios are simulation-based.
- Advanced real-time attack detection is outside the current implementation.
- Integration with external systems would require additional development.
